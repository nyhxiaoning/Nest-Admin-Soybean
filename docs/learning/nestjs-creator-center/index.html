NestJS Creator Center费曼式 0→1 学习路径
学习规则：先尝试用自己的话解释，再展开参考答案。不会复述，就还没有真正掌握。
Repository-grounded learning

认证不是一个 Guard，上传也不是一个 Controller

你要学的是一次请求如何穿过 NestJS 的各层，以及每一层为什么存在。所有讲解都映射到当前 Creator Center 代码。

一句话模型：Middleware 整理“所有来访者”的请求；Guard 决定“这个人能不能进”；Interceptor 包围执行过程；Pipe 检查“带来的数据”；Controller 接单；Service 做业务；Storage/Repository 接触外部世界。

01｜先看全景：把 NestJS 想成一栋办公楼

费曼法第一步不是背装饰器，而是把抽象概念压缩成你能讲给别人听的模型。

Module

楼层与配线图

声明这个业务区有哪些 Controller、Provider，以及需要从其他模块借哪些能力。它负责“装配”，不负责业务。

Controller

前台接待

理解 HTTP：路径、方法、Body、文件和响应。它把工作交给 Service，不应该堆复杂业务。

Provider / Service

真正办事的人

通过依赖注入获得数据库、Redis、JWT 或 Storage，完成登录、校验和文件保存。

Middleware

大楼入口设施

路由处理之前运行，适合解析请求体、限流、压缩、Cookie、请求 IP。它通常不知道最终 Controller 的业务语义。

Guard

门禁

知道当前 Controller/Handler，返回能否继续。Creator JWT 校验放在这里，而不是 Middleware。

Interceptor

执行传送带

包住 Controller 的前后阶段。文件上传的 FileInterceptor 在进入方法前把 multipart 解析成 Multer File。

当前项目最容易误解的点：@NotRequireAuth() 不是“此接口不鉴权”。它只让后台管理端的全局 JwtAuthGuard 放行；Creator Controller 随后用自己的 CreatorJwtGuard 鉴权。

复述 1

假设你要向一个没学过 NestJS 的同事解释：为什么 Module 不是 Service？请用两句话写下来。

展开参考解释

Module 像装配清单，告诉 Nest 哪些对象要创建、如何互相可见；Service 是被创建出来执行具体业务的对象。Module 不接请求也不操作数据。

02｜一条请求到底先经过谁？

点击每一步。只有能说清顺序，你才知道代码应该放到哪里。

核心顺序：Middleware → Guard → Interceptor（前）→ Pipe → Controller/Service → Interceptor（后）→ Exception Filter（发生异常时）。

当前 Creator 图片请求

rateLimit/compression/helmet → 全局 Guards → CreatorJwtGuard → FileInterceptor → @UploadedFile() → UploadService → Storage。

当前 Creator JSON 请求

专用 20 MiB JSON Parser → 通用中间件 → Guards → Validation/Controller → CreatorJsonStorage.store()。

装配位置：main.ts · app.module.ts

复述 2

为什么“验证用户是否登录”更适合 Guard，而不是 Middleware？

展开参考解释

Guard 能读取 ExecutionContext，知道当前 Controller、Handler 和装饰器元数据，因此能根据路由语义决定是否放行；Middleware 更靠近底层 HTTP，适合通用预处理，不适合表达路由权限策略。

请求用户

  return this.service.doSomething(session.id)
}

不要这样做：把密钥写入源码、把完整用户对象塞进 JWT、只解码不验签、只信 JWT 不检查服务端撤销能力、在日志中打印 Token。

04｜Middleware：先处理 HTTP，再谈业务

当前 AppModule 的 configure() 没有注册 HTTP Middleware；主要中间件通过 main.ts 的 app.use() 安装。租户 middleware 是 Prisma 数据库中间件，不是 HTTP 中间件。

需求应该放哪里原因
JSON Body 最大 20 MiBMiddleware / body parserController 执行前必须先把字节解析为对象
当前用户是否登录Guard需要路由元数据和明确的放行/拒绝语义
手机号格式DTO + Pipe这是输入契约验证
multipart 文件解析Interceptor围绕 Handler，把流转换为 Express.Multer.File
统一响应结构Interceptor在 Controller 返回后包装结果
业务异常转 HTTP 响应Exception Filter集中处理抛出的异常

为什么 JSON 上传必须先注册专用 parser？

// bodyParser: false 后，顺序由项目自己控制
app.use('/api/creator/uploads/json', json({ limit: '20mb' }))
app.use(json({ limit: '100kb' }))

Express 按注册顺序处理。Creator JSON 路径先命中 20 MiB 解析器；普通接口仍受 100 KiB 边界保护。如果把通用 parser 放前面，大 JSON 会在到达 Controller 前直接失败。

从零写一个 Nest Middleware

@Injectable()
export class RequestContextMiddleware implements NestMiddleware {
  use(req: Request, res: Response, next: NextFunction) {
    req.requestId ||= randomUUID()
    next() // 不调用就不会继续
  }
}

export class FeatureModule implements NestModule {
  configure(consumer: MiddlewareConsumer) {
    consumer.apply(RequestContextMiddleware).forRoutes('creator')
  }
}
判断口诀：“所有请求先整理”用 Middleware；“这扇门能不能进”用 Guard；“参数合不合法”用 Pipe；“执行前后都要插手”用 Interceptor。

源码：main.ts · app.module.ts

06｜从零实现：受保护的头像上传模块

不要先复制代码。按“契约 → 装配 → 门禁 → 业务 → 外部实现 → 测试”的顺序写，你会更清楚每层为什么存在。

最小装配骨架

@Module({
  imports: [CreatorAuthModule],
  controllers: [AvatarController],
  providers: [
    AvatarService,
    LocalAvatarStorage,
    { provide: AvatarStorage, useExisting: LocalAvatarStorage },
  ],
})
export class AvatarModule {}

@Controller('creator/avatar')
@NotRequireAuth()
@IgnoreTenant()
@UseGuards(CreatorJwtGuard)
export class AvatarController {
  @Post()
  @UseInterceptors(FileInterceptor('file', { limits: { fileSize: 2 * 1024 * 1024 } }))
  upload(@CreatorUser() session: CreatorSession, @UploadedFile() file: Express.Multer.File) {
    return this.avatarService.upload(session.id, file)
  }
}
你真正学会的标准：把 LocalAvatarStorage 换成 OSSAvatarStorage 时，Controller 和 AvatarService 不需要改；把 Creator 鉴权换掉时，文件存储实现不需要改。这就是边界清晰。

07｜费曼检验：不要看答案先选

每道题都对应实际代码决策。答错不是失败，而是精确发现知识缺口。

1. 为什么 Creator Controller 同时出现 @NotRequireAuth() 和 @UseGuards(CreatorJwtGuard)？

2. 图片 multipart 字节是谁转换成 Express.Multer.File？

3. Logout 后 JWT 还没过期，为什么也不能继续访问？

4. 哪个需求最适合 Middleware？

5. OSS 直传为什么比后端中转更适合大文件？

最终复述

请不用“框架就是这样规定的”这句话，向一个前端同事解释：登录后上传一张图片，从 Axios 到磁盘一共发生了什么？

检查是否覆盖关键节点

你的解释应包含：Pinia Token → Axios Authorization → 全局后台 Guard 跳过 → CreatorJwtGuard 验 JWT/Redis/账号 → FileInterceptor/Multer → UploadedFile → Service 校验 → Storage 按 Creator ID 写入 → 返回静态 URL。能解释每一步的责任，就达到了第一阶段目标。
