# Prisma 初始化与 Server 启动问题复盘（1112）

## 一、问题概述

启动 server 时，TypeScript 出现大量 `TS2305` 错误，例如：

```text
Module '"@prisma/client"' has no exported member 'Prisma'.
Module '"@prisma/client"' has no exported member 'PrismaClient'.
Module '"@prisma/client"' has no exported member 'SysAuditLog'.
```

最终编译器报告约 197 个错误。错误分布在 Prisma 基础设施、分页工具、查询构造器、租户扩展、中间件、业务仓储及测试代码中。

本次排查还发现了两个相互独立的后续问题：

1. Nest watch 模式的编译产物入口异常。
2. 本机 PostgreSQL 与 Docker PostgreSQL 同时占用 5432，导致应用连接到了错误的数据库实例。

## 二、核心结论

Prisma Client 初始化失败的主因是 **pnpm 安装时跳过了 Prisma 的构建脚本**，不是 Node.js 版本问题。

仓库使用 pnpm 10.5.0。安装记录 `node_modules/.modules.yaml` 的 `ignoredBuilds` 中包含：

```text
@prisma/engines
prisma
@prisma/client
```

这导致：

1. Prisma 的 macOS ARM64 引擎没有下载。
2. `.prisma/client` 没有生成。
3. `@prisma/client` 只剩下转导声明，无法提供 `Prisma`、`PrismaClient` 及模型类型。
4. 所有依赖 Prisma 类型的代码产生连锁 TS2305 错误。

缺失的关键引擎包括：

```text
libquery_engine-darwin-arm64.dylib.node
schema-engine-darwin-arm64
```

实际解析到的版本一致：

```text
prisma:         5.22.0
@prisma/client: 5.22.0
```

因此，本次故障不是 Prisma CLI 与 Client 版本不一致造成的。

修复后，Prisma Client 在当前 Node.js v23.7.0 下成功生成，两个 ARM64 引擎也能正确解析。这进一步证明 Node.js 不是本次故障的直接原因。

不过 Node 23 属于非 LTS 版本。为减少 NestJS、Prisma、构建工具及原生依赖的兼容性风险，开发环境仍建议统一使用 Node 20 或 Node 22 LTS。

## 三、证据与诊断过程

### 1. Prisma Client 生成目录缺失

`node_modules/@prisma/client/index.d.ts` 的内容只是：

```ts
export * from '.prisma/client/default';
```

但对应的 `.prisma/client` 生成产物不存在，因此 TypeScript 无法解析任何 Prisma 导出。

### 2. Prisma 引擎缺失

执行 Prisma 版本检查时，最初出现：

```text
Could not find libquery-engine binary
Could not find schema-engine binary
```

说明不只是 Client 未生成，Prisma 安装阶段需要下载的本机引擎也没有安装完成。

### 3. pnpm 明确跳过构建脚本

`node_modules/.modules.yaml` 中的 `ignoredBuilds` 明确列出了：

```yaml
ignoredBuilds:
  - '@prisma/engines'
  - prisma
  - '@prisma/client'
```

这与引擎缺失和 Client 未生成完全吻合。

### 4. Node.js 不是直接根因

在没有更换 Node.js 的情况下，放行构建脚本并重新生成后，得到：

```text
Query Engine (Node-API): libquery-engine ... darwin-arm64
Schema Engine: schema-engine-cli ... darwin-arm64
Generated Prisma Client (v5.22.0)
```

运行时也确认以下导出存在：

```ts
Prisma
PrismaClient
```

原来的 `@prisma/client` TS2305 错误全部消失。

## 四、修复方案

### 1. 添加 pnpm 构建脚本白名单

在仓库根目录 `pnpm-workspace.yaml` 中加入：

```yaml
onlyBuiltDependencies:
  - '@prisma/engines'
  - prisma
  - '@prisma/client'
```

这样只允许 Prisma 必需的三个包执行安装构建脚本，不会放开所有依赖的脚本权限。

### 2. 重建 Prisma 依赖

在仓库根目录执行：

```bash
pnpm rebuild @prisma/engines prisma @prisma/client
```

### 3. 生成 Prisma Client

在 server 包执行：

```bash
pnpm run prisma:generate
```

生成结果：

```text
Generated Prisma Client (v5.22.0)
```

### 4. 验证结果

验证项目包括：

- Prisma Query Engine 能正确解析。
- Prisma Schema Engine 能正确解析。
- `Prisma` 和 `PrismaClient` 能正常导入。
- 所有 `@prisma/client` TS2305 错误消失。
- Nest development build 成功，退出码为 0。

全量 `tsc` 仍报告部分测试代码类型错误和缺失 mock 文件，但这些是项目原有问题，与 Prisma Client 生成无关。

## 五、`prisma generate` 与 `prisma migrate` 的区别

### 1. 对比表

| 命令 | 处理对象 | 是否连接数据库 | 是否修改数据库 | 主要用途 |
| --- | --- | --- | --- | --- |
| `prisma generate` | 本地 Prisma Client | 通常不需要 | 否 | 生成 ORM 客户端和 TypeScript 类型 |
| `prisma migrate dev` | Schema、迁移文件和开发数据库 | 是 | 是 | 开发环境创建并应用迁移 |
| `prisma migrate deploy` | 已存在的迁移文件和目标数据库 | 是 | 是 | 测试、预发布或生产环境应用迁移 |
| `prisma migrate status` | 数据库迁移状态 | 是 | 否 | 检查迁移是否一致、是否待执行 |
| `prisma migrate reset` | 整个开发数据库 | 是 | 是，且具有破坏性 | 删除并重建数据库后重新迁移 |
| `prisma db push` | Schema 和数据库结构 | 是 | 是 | 不创建迁移历史，直接同步结构 |

### 2. `prisma generate`

`generate` 读取：

```text
prisma/schema.prisma
```

然后生成：

```text
PrismaClient
Prisma 命名空间
模型类型
查询参数类型
运行时 Client 文件
```

它不会创建数据库、创建表或插入种子数据。

适合在以下场景执行：

- 第一次安装依赖后。
- 修改 `schema.prisma` 后。
- 删除或重新安装 `node_modules` 后。
- 切换 Prisma 版本后。
- 出现 `PrismaClient` 或模型类型无法导出时。

### 3. `prisma migrate dev`

`migrate dev` 用于开发环境，大致流程如下：

```text
schema.prisma
    ↓
比较数据库结构和迁移历史
    ↓
生成新的迁移 SQL
    ↓
写入 prisma/migrations
    ↓
应用迁移到开发数据库
    ↓
通常继续运行 generator
```

该命令要求：

- PostgreSQL 已启动。
- 目标数据库可访问。
- 连接账号和密码正确。
- 数据库端口没有连接到错误实例。

### 4. `prisma migrate deploy`

`migrate deploy` 不根据当前 schema 自动创建新迁移，只会执行已经提交到以下目录的迁移：

```text
prisma/migrations/
```

适合 CI、测试和生产部署。推荐显式执行：

```bash
prisma generate
prisma migrate deploy
```

不要依赖 `migrate deploy` 自动生成 Prisma Client。

### 5. `prisma migrate reset`

该命令会删除并重建开发数据库，属于破坏性操作：

```bash
prisma migrate reset --force
```

本项目的 `prisma:init` 包含 `migrate reset --force`，只适用于数据可以丢弃的本地开发环境，不得直接用于已有重要数据的数据库。

## 六、数据库连接问题复盘

修复 Prisma Client 后，server 启动时曾出现：

```text
Database `nest_admin` does not exist on the database server at `127.0.0.1:5432`.
```

这不是 `prisma generate` 或 Node.js 导致的，而是本机存在两套 PostgreSQL：

```text
macOS 本地 PostgreSQL：127.0.0.1:5432
Docker PostgreSQL：原计划映射到宿主机 5432
```

本机 PostgreSQL 已经监听 `127.0.0.1:5432`。应用连接该地址时优先命中本地进程，但 `nest_admin` 数据库实际位于 Docker PostgreSQL 中。

为避免停止或修改本地 PostgreSQL，本次采用：

```text
Docker PostgreSQL 宿主机端口：5433
Docker Redis 宿主机端口：6379
server 临时环境变量：DB_PORT=5433
```

使用 5433 后，Prisma、PostgreSQL 和 Redis 均成功连接。

如果希望后续直接运行默认开发命令，需要选择一种持久方案：

1. 在 `.env.development` 中将 `DB_PORT` 持久设置为 `5433`。
2. 停止本机 PostgreSQL，让 Docker PostgreSQL 使用 `5432`。
3. 不使用 Docker PostgreSQL，在本机 PostgreSQL 中创建并初始化 `nest_admin`。

建议采用方案 1，避免影响本机已有 PostgreSQL 服务。

## 七、Nest 启动方式问题

Prisma 修复后，Nest watch 模式曾出现：

```text
Cannot find module './config/index'
Cannot find module 'dist/main'
```

这是编译产物或 watch 入口路径问题，与 Prisma Client 生成问题相互独立。

为了完成本次验证，使用 TypeScript 入口直接启动：

```bash
NODE_ENV=development DB_PORT=5433 \
node -r ts-node/register/transpile-only \
     -r tsconfig-paths/register \
     src/main.ts
```

该方式成功启动服务。后续如果要恢复标准 `nest start --watch`，应单独排查 `nest-cli.json`、`tsconfig.build.json`、`dist` 输出结构及 watch 模式删除输出目录的时序。

## 十、推荐的开发环境初始化顺序

### 1. 安装依赖并生成 Client

```bash
pnpm install
pnpm rebuild @prisma/engines prisma @prisma/client
pnpm --filter @nest-admin/server prisma:generate
```

### 2. 启动 PostgreSQL 和 Redis

确认数据库端口与 `.env.development` 一致。如果本机 5432 已被占用，建议让 Docker PostgreSQL 使用 5433。

### 3. 应用数据库迁移

开发环境需要创建新迁移时：

```bash
pnpm --filter @nest-admin/server prisma:migrate
```

只需要应用已有迁移时：

```bash
pnpm --filter @nest-admin/server prisma:deploy
```

### 4. 初始化种子数据

```bash
pnpm --filter @nest-admin/server prisma:seed:only
```

### 5. 启动服务

数据库使用 5433 时：

```bash
DB_PORT=5433 pnpm --filter @nest-admin/server dev
```

如果标准 watch 启动仍出现 `dist` 入口问题，可临时使用：

```bash
NODE_ENV=development DB_PORT=5433 \
node -r ts-node/register/transpile-only \
     -r tsconfig-paths/register \
     src/main.ts
```

## 十一、最终结论

本次问题应拆分为三类：

1. **Prisma Client 类型缺失**：pnpm 10 跳过 Prisma 构建脚本，导致引擎和 Client 未生成。
2. **数据库不存在假象**：应用连接到了占用 5432 的本机 PostgreSQL，而目标数据库位于 Docker PostgreSQL。
3. **Nest watch 入口异常**：属于编译输出和运行入口问题，与 Prisma 安装相互独立。

最简总结：

> `prisma generate` 负责生成代码，`prisma migrate` 负责修改数据库；本次 Prisma 类型错误来自 pnpm 安装脚本被跳过，而后续数据库错误来自本机和 Docker PostgreSQL 的端口冲突，不是 Node.js 版本导致的。
